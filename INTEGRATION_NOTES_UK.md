# Бот підтримки + оголошення про затримки (без бекенду, GitHub Pages + Actions)

Застосунок живе на **GitHub Pages** (тільки статичні файли, ніяких POST-запитів
не приймає) і **GitHub Actions** (задачі за розкладом, а не процес, що
постійно висить і слухає з'єднання). Тому "звичайного" бекенду з живим ботом
(long polling / webhook-сервер) тут бути не може — натомість зроблено так:

## Як це працює

1. **Кнопки в застосунку не шлють нічого на сервер.** "Повідомити про
   затримку" і "Зв'язок з підтримкою" відкривають чат із вашим ботом у
   Telegram через deep link (`t.me/<bot>?text=...`) із заздалегідь
   заповненим текстом. Користувачу лишається тільки натиснути "Надіслати"
   в самому Telegram — це вже звичайне повідомлення боту.
   - `src/lib/reportDelay.ts` — скарга на затримку (текст містить прихований
     тег `#delay:<вид>:<номер_маршруту>#`, щоб скрипт міг розпізнати
     структуровані дані).
   - `src/lib/support.ts` — звернення в підтримку (тег `#support#`).
2. **`.github/workflows/telegram-bot.yml`** запускається кожні ~5 хв
   (мінімальний практичний інтервал для GitHub Actions; в пікові моменти
   GitHub може затримувати запуск) і виконує
   **`scripts/process-telegram-bot.mjs`**:
   - забирає нові повідомлення через `getUpdates`;
   - пересилає звернення в підтримку і скарги на затримку адміну
     (`ADMIN_CHAT_IDS`, секрет репозиторію);
   - якщо адмін робить **Reply** на переслане повідомлення прямо в
     Telegram — скрипт пересилає цю відповідь користувачу в приват
     (це і є "йому приходить повідомлення, що я відповів" — нативно, без
     жодного окремого екрану);
   - рахує скарги: якщо на **один маршрут** поскаржилось **≥5** різних
     користувачів за годину (`DELAY_REPORT_THRESHOLD` /
     `DELAY_REPORT_WINDOW_MINUTES`, змінні репозиторію) — пише адміну
     повідомлення з кнопкою "Так, оголосити затримку";
   - після підтвердження (або команди `/alert 27 bus текст...`) створює
     запис в **`src/public/data/route-alerts.json`** на 2 години
     (`DELAY_ALERT_DURATION_HOURS`) і **комітить файл назад у репозиторій**
     — так само, як уже влаштовано з `notifications.json`;
   - GitHub Pages роздає цей JSON як звичайний статичний файл — саме його
     читає фронтенд (`src/lib/routeAlerts.ts`), щоб показати банер на
     сторінці маршруту і бейдж у списку маршрутів.

## Що треба налаштувати

**Secrets репозиторію** (Settings → Secrets and variables → Actions → Secrets):
- `BOT_TOKEN` — токен від [@BotFather](https://t.me/BotFather)
- `ADMIN_CHAT_IDS` — ваш chat_id (можна кілька через кому). Дізнатись:
  напишіть боту `/start` — після найближчого запуску workflow (або
  вручну через "Run workflow") бот відповість і покаже ваш `chat_id`.

**Variables репозиторію** (там же, вкладка Variables) — необов'язково,
є значення за замовчуванням:
- `DELAY_REPORT_THRESHOLD` (за замовч. 5)
- `DELAY_REPORT_WINDOW_MINUTES` (за замовч. 60)
- `DELAY_ALERT_DURATION_HOURS` (за замовч. 2)

**`.env` фронтенду** (Vite, `.env.example` у корені):
- `VITE_TELEGRAM_BOT_USERNAME` — юзернейм бота без `@`

Перший запуск можна зробити вручну: вкладка **Actions** → workflow
"Telegram Bot (support + затримки)" → **Run workflow**.

## Обмеження цього підходу (чесно, щоб не було сюрпризів)

- **Затримка кілька хвилин**, а не миттєво — і скарга, і відповідь адміна
  дійдуть лише на наступному запуску cron (раз на ~5 хв, часом довше).
- **Історії листування в самому застосунку немає** — вся розмова йде
  нативно в Telegram-чаті з ботом (це прямий наслідок відсутності
  бекенду, який міг би безпечно віддавати приватні дані конкретного
  користувача через статичний файл).
- Якщо потрібна **миттєва** доставка і зручний тред просто в застосунку —
  це вже вимагає хоч якогось живого процесу (безкоштовний Cloudflare
  Worker, Render/Fly.io free tier тощо) замість GitHub Actions. Скажіть,
  якщо захочете такий варіант — можу зібрати окремо.
